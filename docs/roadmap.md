# AI Interview Loop MVP 구현 로드맵

이 초안은 [MVP 기획서 v0.15](mvp-spec.md)와 [개발 작업 규칙](../AGENTS.md)을 기준으로 한다. 모든 구현 작업은 미착수 상태다. 사용자 검토와 승인 후 승인된 작업부터 진행하며, 주요 결정은 승인 후 [ADR 양식](adr/template.md)으로 기록한다. 완료 상태는 실제 검증 결과를 확인한 뒤 갱신한다.

## 확정된 요구사항과 설계 경계

- 프런트엔드와 백엔드, 문서는 단일 Git 저장소의 `frontend/`, `backend/`, `docs/`에서 관리한다. [ADR-0002](adr/0002-monorepo.md)
- 답변 수집이 끝나면 음성을 일괄 STT로 변환한다. [ADR-0003](adr/0003-batch-stt-after-answer.md)
- 데스크톱 브라우저에서 한국어 음성 면접을 진행한다. 자기소개서와 기업·직무 조사 자료가 필수이며, 조사 자료는 여러 파일을 허용한다. 포트폴리오는 선택이다. 텍스트 추출 가능한 PDF, Markdown, TXT를 지원하고 기업·직무 정보는 추출 후 사용자 확인을 받는다.
- 음성 질문 재생이 끝나면 10초 준비가 시작된다. 답변 시간은 60·90·120초에서 선택하며 기본은 60초다. 준비 시간 만료나 ‘답변 시작’ 클릭으로 즉시 답변 타이머와 녹음을 시작한다. 답변 시간 만료나 ‘답변 완료’ 클릭으로 즉시 녹음을 끝내고 STT로 전환한다.
- 핵심 질문은 시작 전에 5개를 목표로 생성하며 유효한 질문이 하나 이상이면 진행한다. 자동 재시도 한도 소진 후 실패한 질문은 질문 수와 채점에서 제외하고, 질문 부족으로 검증하지 못한 영역은 미평가로 처리한다. [ADR-0007](adr/0007-question-generation-recovery.md) AI는 추가 검증이 필요한 경우 꼬리질문을 제안하며, 시스템은 핵심별 0~2개, 꼬리질문 전체 최대 10개, 전체 최대 15개와 종료 조건을 통제한다. 질문 수 사용자 설정은 MVP에서 제외한다.
- 질문은 텍스트와 TTS로 전달하고 답변 종료까지 표시한다. 화면에는 현재 질문 번호, 단계, 남은 준비·답변 시간을 표시하며 아바타, 전체·남은 질문 수, 질문 유형은 노출하지 않는다. 마이크 음량은 AI 호출 없이 클라이언트에서 측정하고 평가 점수에 반영하지 않는다.
- Spring Boot 백엔드와 웹 프런트엔드는 사용자 PC에서 실행하고 브라우저는 `localhost`로 접속한다. [ADR-0001](adr/0001-local-web-application.md)
- 백엔드가 개인 API 키로 외부 AI API를 호출한다. 키는 백엔드 프로세스 메모리에 보관한다. 면접 종료나 평가 실패 후에도 유지하며 사용자가 키를 직접 제거하거나 백엔드를 종료하면 사라진다. 코드·로그·영구 저장소에 남기지 않는다. [ADR-0006](adr/0006-process-lifetime-api-key.md)
- 시작 전 첨부 자료 추출 텍스트와 음성의 외부 전송 여부 및 공급자 보관 정책을 안내한다. STT 재시도에 필요한 동안만 임시 음성을 유지하며 성공·건너뛰기·세션 종료 시 앱 내부 사본을 삭제한다.
- 면접 종료 후 동일한 100점 고정 루브릭으로 평가하고, 질문별 답변 텍스트, 점수와 답변 근거, 강점·개선점, 최대 3개의 전체 개선 우선순위를 제공한다. 직무 적합성은 첨부 자료를 근거로 평가한다. 미응답과 근거 부족 처리 및 점수 산정 세부 규칙은 미확정이다. 카메라, OCR, 웹 검색·자동 조사, 지원 자료 직접 입력, 실시간 음성 스트리밍, 계정·결제, 별도 인프라, 공개 웹 서비스 배포와 데스크톱 응용 프로그램 패키징은 이 계획에서 제외한다. 전체 제외 범위는 기획서 8장을 따른다.
- STT 완료 문답과 평가에 필요한 자료·기준을 로컬 영속 저장한다. 면접 상태와 평가 상태를 독립적으로 관리하며, 재시작 뒤 실패한 최종 평가만 재요청할 수 있다. [ADR-0005](adr/0005-interview-record-and-evaluation-retry.md)
- 구체적인 영속 저장 기술은 후속 검토한다. 브라우저와 서버의 상태 책임, 저장 항목, 일반 세션 데이터의 보존 기간, 키 전달 방법, 로컬 UI 서빙 방식, 문서 추출 라이브러리와 AI 공급자는 미확정이다.

## 단계별 구현 및 완료 기준

단계 순서는 기획서 9장을 따른다. 표의 선행 작업은 완료 기준을 검증하는 데 필요한 구현을 뜻한다. 1단계에서는 모의 데이터와 재생 완료 이벤트로 흐름을 검증하며, 실제 면접 시작 조건은 3·4단계 연동과 6단계 통합 검증에서 확인한다.

| 단계·작업 | 선행 작업 | 구현 범위 및 완료 기준 |
|---|---|---|
| 1.1 초기 환경 확인 | 없음 | Java 21에서 Wrapper로 `./gradlew test`와 `./gradlew bootRun`을 실행해 의존성 해석, 컨텍스트 테스트, 로컬 기동을 확인한다. 실패 시 원인과 재현 조건을 기록하고 버전 변경이 필요하면 별도 논의한다. |
| 1.2 설정 화면 | 1.1 | 파일 등록, 기업·직무 확인, 키 입력, 마이크 확인, 면접 시작 UI를 구성한다. 답변 시간 선택지와 기본 60초를 검증하고 질문 수 설정이 없는지 확인한다. 문서와 장치 연동은 후속 단계에서 검증한다. |
| 1.3 진행 상태와 타이머 (F04) | 1.2 | 브라우저의 화면·타이머와 백엔드의 상태 확정 책임을 [ADR-0008](adr/0008-interview-state-ownership.md)에 따라 나눈다. 모의 이벤트로 면접 진행의 설정·질문·준비·답변·STT·다음 질문·종료·오류 중단과 독립적인 평가 생성 상태를 검증한다. 화면에 현재 단계, 현재 질문 번호, 남은 준비·답변 시간과 수집 상태를 표시한다. 전체·남은 질문 수와 핵심·꼬리질문 구분이 노출되지 않는지 확인한다. 재생 완료 후 10초 준비를 시작한다. 준비 시간 만료 또는 준비 중 ‘답변 시작’ 클릭 즉시 답변 타이머와 음성 수집을 시작한다. 답변 시간 만료 또는 답변 중 ‘답변 완료’ 클릭 즉시 수집을 끝내고 STT로 전환한다. 버튼 클릭과 시간 만료가 겹쳐도 백엔드가 답변을 한 번만 접수하고 상태를 한 번만 전환하는지 검증한다. 정상 종료가 자동 평가 요청으로 이어지고 수동 종료와 오류 중단에는 자동 평가가 요청되지 않는지 확인한다. |
| 2.1 마이크 권한과 녹음 (F05) | 1.3 | `localhost`에 접속한 브라우저에서 권한과 입력을 확인한다. 권한 거부·장치 없음 안내를 검증하고 준비 구간에는 녹음하지 않는다. 답변 종료 이벤트에 맞춰 녹음과 장치 사용을 정리하며 카메라 접근 요청이 없는지 확인한다. |
| 2.2 임시 음성 정리 (F05) | 2.1 | 모의 STT로 성공·실패 후 재시도·건너뛰기·세션 종료를 재현한다. 재시도에 필요한 동안만 음성이 남고 각 삭제 경로에서 앱 내부 사본이 정리되는지 확인한다. |
| 2.3 실시간 음량과 저음량 안내 (F05) | 1.2, 1.3, 2.1 | 시작 전과 답변 중 기준선이 있는 실시간 음량 바로 입력을 확인한다. 답변 중 지속적인 기준 미달에는 경고하고 정상 음량 회복 시 자동 해제한다. 짧은 음량 변화와 자연스러운 발화 중 침묵에는 경고하지 않으며 경고 중에도 타이머와 진행이 계속되는지 검증한다. 음성 파형과 음량 측정을 위한 AI 호출이 없는지 확인한다. |
| 3.1 문서 등록·추출과 기업·직무 확인 (F01) | 1.2 | PDF·Markdown·TXT를 각각 검증한다. 자기소개서와 하나 이상의 조사 자료가 있어야 하며 포트폴리오 없이도 진행할 수 있다. 필수 누락, 추출 실패, 기업·직무 정보 부족 또는 불일치에는 재첨부를 안내하고 확인 전에는 시작을 막는다. |
| 3.2 핵심 질문 사전 생성 (F02) | 3.1 | 첫 질문 재생 전에 첨부 자료 기반 핵심 질문 5개를 목표로 준비한다. 지원 동기 1개, 기업·직무 이해도 1개, 직무 역량 및 프로젝트 경험 2개, 협업 및 문제 해결 경험 1개를 검증한다. 문항이 가급적 1~2문장이고 한 번에 하나의 핵심 내용을 묻는지, 유효한 핵심 질문이 1~4개여도 시작하고 0개면 시작하지 않는지, 웹 검색 없이 자료 범위를 지키고 문서 속 지시문을 실행하지 않는지 확인한다. |
| 3.3 질문 재생과 개인 API 키 연결 (F03) | 1.3, 3.2 | 면접관 이미지·아바타 없이 현재 질문 텍스트와 서버 TTS로 질문을 전달한다. 재생 중에는 준비 타이머가 시작되지 않으며, 재생 완료 후 준비로 전환하고 답변 종료까지 같은 질문 텍스트를 유지한다. TTS 실패는 재시도 또는 명시적 건너뛰기로 복구할 수 있다. 실제 호출 전 전송·보관 안내를 확인하고, 백엔드 메모리에 임시 보관한 개인 키로 외부 AI API를 호출하는지 검증한다. 공급자 결정 전에는 모의 어댑터를 사용한다. |
| 4.1 STT 연결 (F05) | 2.2, 3.3 | 답변 종료 후 서버에서 일괄 STT를 실행하고 텍스트를 해당 질문에 연결하고 문답 단위로 로컬 영속 저장한다. 다음 질문 처리 중 오류를 재현해 이미 저장된 문답이 백엔드 재시작 뒤에도 남는지 확인한다. 동일 답변을 중복 처리하지 않으며, 실패 시 재시도 또는 건너뛰기를 제공한다. 빈 결과와 신뢰하기 어려운 결과를 구분할 수 있는지 확인하고 실제 연동에서도 임시 음성 삭제를 검증한다. |
| 4.2 동적 꼬리질문 (F06) | 3.2, 4.1 | 연결된 핵심 질문, 현재 질문, 직전 STT 답변, 첨부 자료와 이전 문답을 참고한다. 충분히 설명한 답변에서는 생략하고, 추가 검증이 필요한 서로 다른 답변에서는 달라지는 꼬리질문을 한 번에 하나씩 생성하는지 검증한다. 꼬리질문이 가급적 1~2문장으로 하나의 핵심 내용만 묻는지 확인한다. 평가·힌트는 노출하지 않는다. 빈 답변과 불확실한 STT에서 답변을 지어내지 않고 합의된 복구 흐름을 따르는지 확인한다. |
| 4.3 시스템 질문 진행 제어 (F02·F06) | 1.3, 3.2, 4.2 | 핵심 질문을 원칙적으로 유지한다. 꼬리질문 0·1·2개와 한도 초과 제안을 검증한다. 전체 꼬리질문 최대 10개, 전체 질문 최대 15개를 지키고 꼬리질문 한도나 재시도로 유효한 핵심 질문이 누락되지 않도록 한다. 유효 핵심 질문이 5개 미만인 경로와 최대 15개 경로를 검증하고, 정상 종료 및 수동 종료가 시스템에서 처리되는지 확인한다. |
| 4.4 질문 제시 전 필터링 (F02·F06) | 3.3, 4.3 | 핵심 질문과 꼬리질문을 화면 표시와 TTS 재생 직전에 검토한다. 차단된 핵심 질문은 같은 평가 영역에서, 차단된 꼬리질문은 현재 핵심 질문과 답변의 같은 검증 목적을 유지해 다시 생성하고 재검사한다. 필터를 통과한 질문만 화면과 TTS에 전달되는지 확인한다. 두 유형 모두 생성 실패나 필터 차단으로 자동 재시도 한도를 소진하면 해당 질문을 집계에서 제외하고 사용자 개입 없이 다음 질문이나 종료 단계로 전환하는지 검증한다. |
| 5.1 평가 전 질문 필터링과 고정 루브릭 평가 (F07) | 4.4 | 정상 종료 후 면접 기록과 평가에 필요한 기업·직무 자료 및 적용한 평가 기준의 저장을 완료한 뒤 평가를 요청한다. 평가의 성공·실패가 이미 완료된 면접의 진행 상태나 기록을 바꾸지 않는지 확인한다. 수동 종료 시 자동 평가 호출이 없고, 사용자 요청 시 종료 시점까지 저장된 문답으로 피드백을 생성하는지 확인한다. 5개 항목 배점이 20·20·25·20·15이며 합계가 100점인지 확인하고, 합의된 산정 규칙에 따른 점수 범위와 합산을 검증한다. 제시된 질문 중 부적절한 문항과 해당 답변이 감점 없이 채점 대상에서 제외되는지 확인한다. 생성에 실패한 질문은 채점에서 제외하고 질문 부족으로 검증하지 못한 영역은 미평가로 처리하는지 확인한다. 저장된 답변이 없거나 필터링 뒤 채점 대상이 0개인 경우 AI 채점·피드백 호출 없이 안내하고 저장된 기록을 열람할 수 있는지 확인한다. 답변 근거를 원문에, 직무 적합성 근거를 첨부 기업·직무 자료에 대조한다. 미응답·근거 부족은 승인된 처리 방식으로 검증하며 입력 음량, 비언어 요소와 합격 예측은 평가에서 제외한다. |
| 5.2 결과·기록 화면과 평가 재시도 (F07) | 5.1 | 종료 후 질문별 답변 텍스트, 루브릭 점수와 평가 근거, 강점·개선점, 최대 3개의 개선 우선순위를 표시한다. 결과에는 평가 전 필터링 이후 실제 평가에 사용된 답변 범위를 표시한다. 재시작 뒤 이전 면접 기록 열람·삭제를 확인한다. 오류로 중단된 면접에서는 이어하기와 부분 평가를 제공하지 않는다. 정상 종료 후 평가에 실패한 기록은 키를 다시 입력해 평가만 재요청할 수 있는지 확인한다. 삭제 후 해당 면접의 앱 내부 데이터를 다시 사용할 수 없고, 삭제 뒤 지연 응답으로 세션이 복원되지 않는지 확인한다. |
| 6.1 통합·예외 검증 | 2.3, 3.3, 4.4, 5.2 | 가상 지원 자료로 설정부터 삭제까지 재현한다. 질문 표시와 TTS 전환, 진행 정보 노출 범위, 마이크 사전 점검, 일시적 침묵·지속 저음량·정상 회복에서의 안내 동작을 확인한다. 평가 입력과 점수 산정에 음량을 사용하지 않는지 검증한다. 같은 입력을 반복 평가해 항목별 점수 편차를 비교하고, 실제 답변에 없는 근거와 첨부 자료에 없는 직무 적합성 판단을 찾을 수 있는지 확인한다. 10초 준비와 기본 60초 답변의 자동 전환, 두 버튼으로 즉시 전환, 각 단계의 시간 만료와 클릭 경합, 빈 답변, 권한 거부, STT·LLM·TTS 실패와 재시도·건너뛰기, 기존 답변 보존을 확인한다. 진행 도중 장애와 최종 평가 실패를 각각 재현하고 백엔드를 재시작해 중단 기록 열람과 정상 종료 기록의 평가 재요청을 검증한다. 사용자 PC에서 백엔드와 프런트엔드를 기동해 브라우저의 `localhost` 접속을 확인한다. 면접 종료와 평가 실패 뒤 키가 유지되고, 키 직접 제거와 백엔드 재시작 뒤 기존 키를 다시 사용할 수 없는지, 코드·로그·영구 저장소에 키가 남지 않는지, 종료 경로별 음성이 정리되는지 확인한다. 모의 테스트와 실제 공급자 검증 결과를 구분하고, 실제 호출로 답변에 따른 꼬리질문을 최소 한 번 확인한다. |
| 6.2 실행 문서와 MVP 확인 | 6.1 | README에 백엔드·프런트엔드 로컬 기동과 `localhost` 접속 절차, Java·Gradle 및 브라우저·마이크 조건, 개인 API 키 설정과 수명, 데이터 전송 및 보관 범위를 기록한다. README만으로 로컬 재현이 가능한지 확인하고 기획서 10장의 완료 조건별 검증 결과를 기록한다. 기획서 11장의 연습 유용성, 질문·꼬리질문 적합성, 피드백 실행 가능성, AI 대기 시간은 실제 사용 후 관찰 결과를 남긴다. |

## 주요 기술적 의사결정과 검토 시점

| 검토 시점 | 결정과 선택지 | 판단 기준과 검증 |
|---|---|---|
| 1.2·1.3 착수 전 | **상태 전이와 데이터 수명주기.** 브라우저와 백엔드의 진행 상태 책임은 ADR-0008을 따른다. 이벤트 전달, 화면 동기화, 문서·답변·음성의 처리 위치와 수명을 검토한다. | 타이머 만료와 시작·완료 버튼 클릭의 경합, 새로고침, 처리 중 수동 종료와 삭제를 상태 전이표로 확인한다. 기록 복구는 ADR-0005를 따른다. |
| 1.2 착수 전 | **UI 구성과 서빙 방식.** Spring Boot에서 정적 UI를 제공하거나 프런트엔드 소스와 빌드를 분리한다. 전자는 로컬 실행 경로가 짧고, 후자는 UI 도구 선택 폭이 넓지만 빌드와 통합 설정이 늘어난다. | 기존 백엔드와의 결합, 구현량, 상태 관리, 로컬 실행 재현성을 기준으로 세 화면과 마이크 접근 경로를 검토한다. |
| 2.1 착수 전 | **녹음 포맷과 임시 음성 전달.** 브라우저 메모리에서 녹음본을 유지하거나 서버에서도 재시도용 사본을 짧게 유지한다. 전자는 서버 저장 범위를 줄이고, 후자는 재전송 부담을 줄이는 대신 서버 정리 책임을 늘린다. | 대상 브라우저의 포맷과 STT 입력 호환성, 최대 120초 녹음 크기, 실패·이탈 시 정리 경로를 확인한다. 공급자 확정 전에는 실제 호환 여부를 미검증으로 둔다. |
| 2.3 착수 전 | **클라이언트 음량 측정과 경고 조건.** 피크 기반 측정과 일정 구간의 평균 에너지 기반 측정, 단일 기준선과 경고·해제 조건을 분리하는 방식을 비교한다. 피크는 순간 변화에 민감하고, 평균은 표시를 안정화할 수 있으나 반응이 늦어질 수 있다. | 음량 기준과 단위, 측정 구간, 기준 미달 지속 시간, 자연스러운 침묵과 저음량 발화의 구분, 정상 회복 조건을 검토한다. 대상 데스크톱 브라우저에서 정상 발화, 짧은 침묵, 지속 저음량, 음량 회복을 재현해 오경고와 반응 지연을 비교한다. |
| 3.1 착수 전 | **문서 추출과 확인 기준.** PDF 추출 라이브러리와 TXT·Markdown 처리 방식, 파일·추출 텍스트 한도, 기업·직무 후보의 규칙 기반 또는 AI 기반 추출을 검토한다. 규칙 기반은 외부 전송을 줄이고, AI 기반은 자유 형식에 대응할 수 있으나 키와 사전 전송 안내가 필요하다. | 한국어 PDF, 빈 파일, 스캔본, 복수 조사 자료의 불일치, 정보 부족 사례로 추출과 재첨부 흐름을 비교한다. AI를 추출에 사용한다면 최초 전송 전에 안내가 표시되도록 순서를 합의한다. |
| 3.2·3.3 착수 전 | **AI 공급자와 키 전달.** STT·LLM·TTS를 한 공급자에서 사용하면 키 설정이 단순해지고, 기능별 공급자를 고려하면 선택 폭이 넓어지지만 키 입력과 운영 흐름이 복잡해진다. 키 보관 위치와 수명은 ADR-0006을 따른다. 브라우저에서 백엔드로의 키 전달 방법과 호출 오류 시 처리를 검토한다. | 사용자 키 설정 요구사항, 한국어 품질, 비용, 지연, 음성 포맷, 데이터 보관 조건과 키 노출·삭제 경로를 확인한다. 확정 전에는 질문 생성·STT·TTS·평가 어댑터를 모의 응답으로 검증한다. |
| 1.3 착수 전 초안, 3.2·4.3 착수 전 검토 | **핵심 질문과 꼬리질문의 진행 제어.** 핵심 질문 목록과 현재 위치·누적 수를 명시적으로 관리하는 방식과, 문답 기록에서 진행 상태를 계산하는 방식을 비교한다. 전자는 상태 전이를 검증하기 쉽고, 후자는 중복 저장을 줄이지만 재시도와 재질문을 기록에서 구분해야 한다. | 핵심 질문의 식별과 보존, 꼬리질문 연결, 카운트 시점, 재질문·재시도·건너뛰기의 영향, 한도 초과 제안의 처리와 정상·수동 종료 규칙을 검토한다. 모의 AI로 최대 경계, 중복 응답, 마지막 핵심 질문의 꼬리질문, 수동 종료를 검증한다. |
| 4.1·5.1 착수 전 | **면접 기록의 영속 저장과 장애 처리.** 로컬 저장 기술, 문답 쓰기 실패 시 진행, 기록 보존 기간, 별도 면접·평가 상태의 복구와 평가 중 기록 삭제를 검토한다. | 문답 저장 직후 장애, 평가 직전 재시작, 중복 재요청과 삭제 뒤 지연 응답을 재현한다. 요청형 피드백 실패 시 재시도 조건을 검토한다. |
| 4.4·5.1 착수 전 | **질문 가드레일.** 제시 전과 평가 전의 판정 기준, 판정 방식, 자동 재시도 한도의 값, 실패 분류, 평가 재시도 시 판정 적용 방식을 검토한다. 한도 소진 후 자동 진행은 ADR-0007을 따른다. | 정상 문항, 제시 전에 차단할 문항, 평가에서 뒤늦게 제외할 문항을 검증한다. 오탐, 모든 문항 차단·제외, 판정 실패와 지연도 검토한다. |
| 5.1 착수 전 | **루브릭 점수 산정과 근거 검증.** 면접 전체를 항목별로 직접 채점하는 방식과 문답 단위 근거·점수를 모아 집계하는 방식을 비교한다. 전자는 집계가 단순하고, 후자는 점수 추적이 쉽지만 꼬리질문 수 차이를 반영하는 규칙이 필요하다. | 채점 단위, 항목별 점수 구간과 합산, 미응답·근거 부족, 간결성에 필요한 시간 정보, 답변·자료 근거를 표시하고 검증하는 방식 및 반복 평가의 허용 편차를 검토한다. 동일 입력 반복과 근거 불일치 예시로 비교한다. |
| 4.1·4.2·5.1 착수 전 | **AI 응답 형식과 복구 규칙.** 구조화 응답 지원 여부와 서버 검증 방식, 불확실한 STT 판정 신호, 단계별 재시도·건너뛰기 이후의 전이를 검토한다. | 잘못된 응답 형식, 무음, 근거 없는 질문·평가, 공급자 실패를 모의 재현한다. 유효 핵심 질문이 0개일 때의 안내와 평가 생성 실패 시 화면에 표시할 상태 및 보존할 데이터를 검토한다. |

로드맵 1.1에서 기존 백엔드 빌드·기동 환경을 확인한다. 설정 화면과 진행 흐름을 구현하기 전에 로컬 UI 서빙 방식과 ADR-0008에 따른 이벤트 전달 및 상태 전이를 검토한다.
